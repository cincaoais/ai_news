# ai-news

A daily Telegram news digest, generated by the DeepSeek API (deepseek-chat) and scheduled
fully in the cloud on GitHub's free Actions minutes. This is the operator manual: what
runs when, how to switch topics, how to read a failure, and what's still rough at the
edges.

## What this is

Every morning, a script-fetched batch of RSS/news candidates for your active topic
profile is sent to the DeepSeek API, which picks the 5-8 most important ones by index and
writes a 1-2 sentence "why it matters" summary for each -- the model never types a URL or
invents a fact, it only selects and summarizes from what the fetcher already found. A
second script then builds the HTML message (attaching the real URLs itself), sends it to
your Telegram, and commits the day's state (seen-URL log + last digest) back to this repo
so tomorrow's run knows what not to repeat. The whole thing runs unattended on a cloud
scheduler -- no PC left on; the editorial step costs a fraction of a cent per run via the
DeepSeek API.

```
 config/profiles/*.yaml, CLAUDE.md, scripts/*.py   (this repo, cloned fresh each run)
              │
              ▼
 SCHEDULER: GitHub Actions cron, daily 07:47 MYT → run_digest.py (see "Scheduler
 operations" below; manual workflow_dispatch also works, e.g. mock/dry-run)
              │
              ▼
 (1) fetch_news.py     -- feeds + Google News fallback + market snapshot
                          → work/candidates.json (indexed, deduped, freshness-checked)
 (2) DeepSeek API      -- prompt embeds candidates.json + state/last_digest.md
                          + CLAUDE.md rules → work/selection.json (5-8 items, BY INDEX ONLY)
 (3) build_and_send.py  -- validates selection, builds HTML, sends to Telegram
 (4) update_state.py    -- records sent items, rewrites last_digest.md, commits + pushes
              │
              ▼
 any step failing → scripts/notify_failure.py alerts your Telegram (channel 1)
 whole pipeline never running at all → .github/workflows/watchdog.yml (channel 2)
```

See `docs/02-PLAN.md` for the full design rationale (written for the original Claude-era
architecture). The scheduled GitHub Actions workflow performs all steps in code via
`scripts/run_digest.py`; `RUNBOOK.md` is retired (it was the Claude Code Routine's
instruction set).

## Daily operation

- **What arrives when**: the scheduler (a GitHub Actions cron) fires at 07:47 MYT daily;
  queueing and run time mean the message actually lands close to **~08:00 MYT**. One
  message, 5-8 items, for whichever profile is currently active.
- **"Quiet news day" note**: if the fetcher's lookback window (widened once automatically)
  still turns up fewer than 3 fresh candidates, the digest still sends -- the daily
  message is the heartbeat, never skipped -- but carries an `<i>Quiet news day.</i>` line
  under the header instead of pretending a full day's worth of news existed.
- **Feed-health footer**: if one or more of the profile's source feeds was skipped that
  day (stale -- its newest entry was already >48h old -- or dead -- network/parse
  failure), the digest ends with a one-line note: `note: N source feeds skipped (details
  in repo logs)`. This is informational only (the digest still has enough from its
  healthy feeds); it does not name which feed, by design -- check the fetch step's logs
  (a Routine run's own transcript, or the Actions run log) for which one and why.

## Switching topic profiles

1. Edit `config/config.yaml`, change `active_profile:` to one of the profile names below.
2. Commit and push.
3. The next scheduled run (Routine or Actions) reads the new value and switches sources,
   editorial focus, and (if enabled) market snapshot accordingly -- no code changes, no
   redeploy.

| Profile | Focus | Market snapshot |
|---|---|---|
| `finance_metals` (default) | US stocks, gold/metals, global macro | Yes (S&P, Nasdaq, gold, USD/MYR) |
| `sports` | Global + Malaysia sports | No |
| `entertainment` | Entertainment / Hollywood / global media | No |
| `malaysia_politics` | Malaysia domestic + global politics | No |

Same-day guard note: `build_and_send.py` refuses a second real send for the *same*
profile on the *same* MYT calendar day (prevents duplicate digests from overlapping
schedulers or a manual re-run). Switching profiles mid-day is exactly how Slice 5's live
Routine test avoided tripping that guard against a profile already sent that day. This
guard reads this clone's own (possibly stale) copy of `state/last_digest.md` -- it is
**best-effort**, not a hard guarantee, if two schedulers are deliberately run at once;
the rule remains **exactly one scheduler active at a time** (see "Scheduler operations"
below). Two further mechanisms narrow, but don't eliminate, that gap:

- **Pre-send origin re-check**: immediately before the first real send of a run,
  `build_and_send.py` (if a git `origin` remote is configured) runs `git fetch origin`
  and re-reads *origin/main*'s own `state/last_digest.md` one more time, aborting like
  the same-day guard above if it already shows today's profile sent. This shrinks the
  race window from "however stale this clone/session is" down to the few seconds the
  fetch takes. Any git/network hiccup here is logged as a warning and the send proceeds
  -- this check is never allowed to crash a send that would otherwise go through cleanly.
- **Send-progress resume**: if a real send is interrupted partway through (e.g. Telegram
  rejects message 3 of 4), `build_and_send.py` records progress in
  `work/sent_progress.json` after every successfully delivered message. The next run for
  the same date + profile resumes from the first message *not yet* recorded as sent,
  rather than re-sending (and duplicating) the whole digest from scratch. The progress
  file is deleted once the full send completes; `--dry-run` never reads or writes it.

## Adding a new profile

Create `config/profiles/<name>.yaml` matching this schema exactly (all fields required
unless noted):

```yaml
name: my_new_profile            # must match the filename
description: One-line description
language: en
feeds:                          # each: url + human label; every feed is optional at
                                 # runtime (dead/stale ones are skipped, not fatal)
  - {label: Some Source, url: "https://example.com/rss"}
gnews_fallback:                 # Google News RSS pseudo-search queries; "when:1d" is
                                 # REQUIRED (default sort is relevance, not recency)
  - "some topic when:1d"
gnews_locale: {hl: "en-MY", gl: "MY", ceid: "MY:en"}   # OPTIONAL -- omit for the default
                                 # en-US/US/US:en locale on Google News results; only
                                 # malaysia_politics.yaml sets this today
market_snapshot:
  enabled: false                 # set true + list symbols for a Yahoo-chart-API snapshot
  symbols: []
editorial_focus: >               # injected into the LLM prompt as this profile's lens
  What counts as important for this profile, in one or two sentences.
```

**Live-verify every feed before adding it.** A feed URL that looks right on paper can
still be dead, bot-walled, or a "frozen but returns 200" trap (`docs/01-RND.md` found
several real examples of exactly this). Fetch it yourself and confirm it returns fresh
entries before it goes in a profile -- `lib/feeds.py`'s freshness check will silently skip
it (logged, not fatal) if it's stale or dead, so a bad feed doesn't break the pipeline,
but it also won't tell you *why* your new profile's digest looks thin unless you check
the logs.

**Never add these** (live-verified dead, blocked, or a frozen-but-200 trap as of
2026-07-31 -- re-verify independently before ever reconsidering one): Reuters RSS, Kitco
RSS, Stooq, ESPN RSS, The Star RSS, The Edge RSS, MarketWatch MarketPulse.

## Scheduler operations

Exactly **one** scheduler should be active at a time. Today there is one: the GitHub
Actions cron in `.github/workflows/digest.yml`. (The old primary -- a Claude Code Routine
on claude.ai -- was **retired 2026-08** when the Claude subscription was dropped; see the
`RUNBOOK.md` banner for what it was.)

### The scheduler: GitHub Actions

`.github/workflows/digest.yml` runs the whole pipeline via `scripts/run_digest.py`:
fetch → DeepSeek API editorial step → validate + send → commit state. Its cron fires
**07:47 MYT** daily (`47 23 * * *` UTC) -- an off-hour minute, because GitHub Actions
schedules queue and can slip several minutes during platform load spikes that cluster at
`:00`. Manual runs via the Actions tab:

- **Mock dispatch** (no secrets needed): Actions tab → "Daily digest (Actions scheduler)"
  → "Run workflow" → leave `mock` checked. Fetches real news, substitutes a fixture
  selection instead of calling the LLM API, prints instead of sending, skips the state
  commit.
- **Real dispatch**: uncheck `mock`; leave `dry_run` checked to validate a real DeepSeek
  call without sending/committing, or uncheck both for the full real path. Requires the
  three secrets below.

The editorial step calls `api.deepseek.com` with the `deepseek-chat` model. Everything
the model needs is embedded in the prompt by `run_digest.py` at run time: `CLAUDE.md`'s
editorial rules (read from the repo -- one source of truth), today's `candidates.json`,
yesterday's `last_digest.md` (soft dedup), and the active profile's `editorial_focus`.
The model returns JSON; the wrapper writes `work/selection.json` and validates it before
anything is sent.

## Secrets & credentials

| Secret | Where it lives | How to rotate |
|---|---|---|
| `DEEPSEEK_API_KEY` | GitHub Actions repo secret + local `.env` (dev machine) | Create at platform.deepseek.com (API keys section). Pay-as-you-go: top up a small balance -- a daily digest costs a fraction of a cent. Rotate by generating a new key and replacing the secret in all locations. |
| `TELEGRAM_BOT_TOKEN` | Local `.env` (dev machine) + GitHub Actions repo secret | Message @BotFather `/revoke` on the existing bot (or make a new one), update both locations. |
| `TELEGRAM_CHAT_ID` | Local `.env` + GitHub Actions repo secret | Rarely changes (tied to your Telegram account); re-derive with `python scripts/get_chat_id.py` after messaging the bot once if ever needed. |

`.env` is **local-only and gitignored** -- it's read by `lib/env.py`'s stdlib loader for
manual/dev-machine runs only; GitHub Actions never reads it (it gets these values as
real repository secrets instead, which always win over anything in `.env` if both happen
to be present). Copy `.example.env` to `.env` and fill in real values to run anything
locally.

## Failure handling & alert channels

Three ways a problem becomes visible, by design -- none of them is "check back tomorrow
and notice nothing arrived":

1. **Telegram notifier (in-pipeline failures)** -- every stage of the pipeline
   (fetch/editorial/send/state) routes any exception through
   `scripts/notify_failure.py`, which sends a plain-text (deliberately not HTML --
   immune to whatever malformed content caused the original failure) alert to your
   Telegram, stage-tagged (e.g. `[ai-news alert] fetch: 0 candidates after filtering`).
2. **Watchdog → GitHub e-mail (Telegram-independent)** -- `.github/workflows/watchdog.yml`
   runs daily at 10:37 MYT (no secrets needed) and fails if the most recent commit
   touching `state/` is 26+ hours old. A failing *scheduled* GitHub Actions workflow
   triggers GitHub's own native failure e-mail to you -- that email IS the alert. This
   exists specifically to catch the two failure classes channel 1 cannot: Telegram
   credentials themselves being dead (so channel 1's own delivery path is broken), and
   the scheduled cron run never having happened at all (so no in-pipeline code ever
   executed to reach channel 1 in the first place).
3. **The digest workflow's own failure e-mail (GitHub platform behavior)** -- a failing
   *scheduled* digest workflow also triggers GitHub's native "workflow run failed"
   e-mail to the repo owner. An extra, Telegram-independent signal on top of channel 1;
   like the watchdog, it needs no code of ours.

**What a `state:`-tagged alert specifically means**: if `update_state.py` fails (its
commit/push to `state/` didn't go through, even after its rebase-retry), **the digest was
already sent successfully** -- only the dedup bookkeeping failed to record it. Nothing was
lost, but tomorrow's run may repeat one or more of today's stories, since
`state/seen.jsonl` and `state/last_digest.md` were never updated to reflect what just went
out. The raised error message says this explicitly (`"digest WAS already sent; only the
dedup state failed to push -- tomorrow's digest may repeat today's stories"`); no urgent
action is needed beyond eventually resolving whatever blocked the push (e.g. a persistent
git conflict) before it affects more than one day's dedup.

**If no digest has arrived by 9 AM MYT**, check in this order:
1. Telegram itself -- muted chat, or the bot blocked.
2. **GitHub Actions → digest workflow** -- did today's scheduled run appear in the run
   list at all? Did it succeed? (GitHub Actions schedules can occasionally be skipped or
   delayed during platform incidents.)
3. **GitHub Actions → watchdog workflow** -- is it red? Its failure message names the
   likely cause (stale `state/`, dead Telegram credentials, dead DeepSeek key or empty
   balance).
4. **DeepSeek account** -- is the API key still valid and the balance topped up? A dead
   key or exhausted balance fails the editorial step cleanly and looks identical to a
   silent pipeline failure unless you check the run logs.

## Known limitations & backlog

- **Mock-mode index quirk**: when `run_digest.py --mock-claude <fixture>` is used, the
  wrapper still does a real fetch, so a fixture selection's indices can end up paired
  with different (freshly-fetched) articles than whatever the fixture was originally
  written against -- a cosmetic mismatch (headline vs. summary) in mock/test runs only.
  Structurally impossible in production: the real editorial step always writes its
  selection against the exact same run's `candidates.json`, and `run_digest.py` never
  re-fetches between steps.
- **DeepSeek API is the one new external dependency.** The editorial step calls
  `api.deepseek.com`; a network block, revoked key, or exhausted balance fails the run
  (Telegram alert + watchdog + workflow failure e-mail). Cost per daily run is a
  fraction of a cent, but the account needs a topped-up balance -- an empty balance is
  the most likely silent failure mode, so the watchdog message names it explicitly.
- **Cron migration: first-run verification ongoing.** The Actions cron was enabled when
  the DeepSeek swap landed (previously it shipped dormant). Watch the first few
  unattended *scheduled* (not manually triggered) runs land ~08:00 MYT and push
  `state/` as expected, per the watchdog.
- **3-consecutive-scheduled-runs observation window: ongoing.** The old Routine's live
  cycles are recorded in `docs/03-EXECUTION-LOG.md`; three unattended *scheduled*
  Actions cron runs in a row landing and pushing `state/` has not yet been observed
  under the new DeepSeek setup and continues post-swap.
- **`/topic` Telegram-command profile switching is v2**, not built here. `getUpdates`
  (the mechanism a bot uses to read messages sent to it) only retains updates for **24
  hours** -- a `/topic sports` message sent during any gap between daily runs would be
  silently lost, and the offset would need to be persisted across runs. v1's answer is
  the config-file edit in "Switching topic profiles" above, which has no such caveat.

## Development

```
pip install -r requirements.txt
pytest                                    # full suite, network-free, ~a few seconds
pytest -m live                            # + one real-network smoke fetch (excluded by default)
python scripts/fetch_news.py              # writes work/candidates.json for the active profile
python scripts/run_digest.py --dry-run    # full pipeline, real DeepSeek call, prints instead of sending
python scripts/run_digest.py --mock-claude tests/fixtures/mock_selection.json --dry-run --skip-state
                                           # same, but skips the real LLM API call entirely
```

`--dry-run` never sends to Telegram or touches `state/`; `--mock-claude PATH` substitutes
a fixture `selection.json` instead of invoking the real DeepSeek API (used by CI's mock
dispatch and for fast local iteration); the `live` pytest marker is excluded by default
(`pytest.ini`) because it hits real feeds and the real Yahoo chart API -- run it
explicitly when you want that confirmation.
